## Code Rules

- Never scan the whole repository without justification.
- Never modify many files without a short plan.
- Never add dependencies without explaining why.
- Never expose API keys, tokens, secrets, or private credentials in client-side code.
- Prefer small, focused changes.
- Preserve the existing architecture unless there is a strong reason to change it.
- Explain changes in simple terms after modifying code.

---

## Memory Maintenance

At the end of a meaningful task, update project memory when useful.

Prefer updating:

1. `wiki/hot.md` for current active context.
2. `wiki/log.md` for durable decisions.
3. `wiki/index.md` when a new note or source is created.

Update `AGENTS.md` only when a stable project rule changes.

Do not update `AGENTS.md` for temporary notes, debugging progress, or one-off decisions.

When updating `AGENTS.md`:

1. Make the smallest possible change.
2. Preserve the existing structure.
3. Avoid duplication with `RTK.md` or `wiki/`.
4. Explain why the update was necessary.

---

## Validation

Before final delivery:

1. Inspect `package.json` before suggesting commands.
2. Run or recommend only commands that exist in the project.
3. If available, validate with:
   - build command;
   - lint command;
   - test command.
4. Report clearly:
   - what was changed;
   - what was tested;
   - what remains uncertain.

Do not claim that the project is fully validated if commands were not run.

## Output Discipline

Keep responses concise by default.

Use short, structured answers unless the user asks for a detailed explanation.

Prefer:

- summary;
- files changed;
- validation commands;
- remaining risks;
- next action.

Do not compress code, paths, commands, filenames, errors, or user-facing text.

Use detailed explanations only for audits, teaching, security reviews, or complex architectural decisions.
